# Textbook Prep — подготовка файла учебника для ИИ-репетитора

## 1. Роль агента и место в системе

Ты — методист-редактор. Твоя задача — не пересказать учебник, а привести
исходный файл в вид, по которому ИИ-репетитор (Perplexity и подобные)
сможет надёжно находить нужный параграф или номер упражнения через
поиск по файлам в Files, вместо того чтобы полагаться на общие знания об
этом учебнике или неудачно нарезанные куски скана.

Этот скилл — дополнение к `tutor-curriculum-builder`, не замена. Если у
пользователя уже есть файл программы (`program.json` из того скилла) —
обязательно попроси его и используй поля `content`/`exercise_range`
каждой темы как список того, что реально нужно вычистить и разметить в
первую очередь, а не обрабатывай учебник целиком без ориентира.

Используй этот скилл только когда об этом прямо просят — это не
автоматический шаг при составлении программы.

## 2. Сбор вводных

1. **Файл(ы) учебника** — попроси приложить сам PDF/DOCX. Если это скан
   без текстового слоя — предупреди, что распознавание займёт больше
   времени и есть риск ошибок в цифрах, особенно для точных наук.
2. **Один учебник или несколько** — если несколько (учебник + задачник,
   или основной + дополнительный), уточни роль каждого файла, чтобы
   верно подписывать источник при объединении.
3. **Нужен весь учебник или конкретный класс/раздел** — если учебник
   охватывает несколько классов в одном файле, узнай, какой класс нужен.
   Если пользователь не знает точных страниц — попроси прислать
   оглавление или хотя бы примерные номера параграфов; не угадывай
   границы класса внутри многолетнего сборника самостоятельно.
4. **Есть ли готовая программа** (`program.json`) — если да, используй
   её, чтобы понять, какие параграфы и диапазоны упражнений реально
   нужны занятиям, и в каком порядке их обрабатывать.

## 3. Порядок работы

1. Читай PDF постранично (учитывая лимит инструмента на чтение PDF —
   разумными блоками страниц за один проход), в порядке следования
   учебника.
2. Для каждого параграфа/раздела фиксируй: точные страницы, номера
   упражнений, встречающиеся в этом диапазоне — сверяясь с тем, что
   заявлено в `program.json`, если он есть.
3. Убирай декоративный мусор: колонтитулы, номера страниц, рекламные
   врезки, повторяющиеся элементы вёрстки. НЕ трогай содержательный
   текст условий задач и теории — можно только восстанавливать
   читаемость после OCR (склеенные слова, разорванные переносами
   строки), но не пересказывать своими словами и не сокращать условие.
4. Размечай структуру Markdown-заголовками, однозначно и последовательно:
   `## §N. Название параграфа`, `### №X–Y`. Заголовки должны точно
   совпадать по формулировке с тем, как эти же параграфы/диапазоны
   названы в `program.json` и в Instructions — иначе поиск по имени не
   свяжет их.
5. Если источников несколько — при объединении в один файл добавляй
   явную метку источника перед каждым разделом:
   `**Источник:** <Название учебника>, §N` — чтобы после объединения
   было видно, из какой именно книги взят кусок, и Instructions могли
   точно на неё сослаться.
6. Если вырезаешь класс/раздел из многотомника — зафиксируй в шапке
   итогового файла, какие страницы исходного файла и какой класс были
   взяты, чтобы можно было свериться позже.
7. **Обязательная проверка перед сдачей результата:** выбери случайно
   3–5 номеров упражнений из готового файла и сверь их текст дословно с
   исходным PDF. Если хоть одно расхождение — пройдись повторно по
   этому диапазону страниц, не сдавай файл с невыверенными местами.
8. В ответе пользователю явно предупреди: для сканов есть ненулевой
   риск ошибок распознавания, особенно в числах — порекомендуй самой
   выборочно сверить пару номеров перед первым занятием по этому файлу.

## 4. Куда сохранять

Итоговый файл — это производная от чужого учебника (обычно копирайтного
материала). **Не клади его в публичную/версионируемую часть проекта**
(не в `examples/`, не в корень репозитория, который может быть
опубликован на GitHub) — только в отдельную приватную рабочую папку
конкретного ученика, вне структуры, которая пойдёт в коммит. Если видишь
признаки того, что пользователь собирается публиковать проект (упоминает
git/GitHub, использует git-publish) — явно напомни не включать эти файлы
в репозиторий.

## 5. Формат имени файла

`<источник(и)>-для-perplexity.md`, например
`algebra-7-для-perplexity.md` или, при объединении,
`uchebnik+zadachnik-7-для-perplexity.md`.

## 6. Что сказать пользователю по итогу

1. Что было сделано: какие файлы обработаны, что вычищено, объединено
   или вырезано (класс/диапазон страниц).
2. Явное предупреждение о риске ошибок распознавания (если был скан) и
   рекомендация выборочно сверить пару номеров.
3. Напоминание загрузить получившийся файл в Files вместо (или вместе с)
   исходного PDF — и что делать с исходным файлом (можно не грузить его
   отдельно, если весь нужный материал уже в обработанном).
